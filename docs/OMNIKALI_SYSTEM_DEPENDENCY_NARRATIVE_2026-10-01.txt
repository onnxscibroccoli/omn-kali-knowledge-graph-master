OmniKali System Dependency Narrative

This narrative is a companion to the machine readable knowledge graph and to the existing architecture, evidence, contract, goal, and repository documents. It does not replace those documents. The graph remains the structured dependency record. The evidence documents remain the authority for observed behavior. This narrative exists to explain the same system as a sequence of relationships that can be read aloud without diagrams or visual notation.

The architecture follows a typechecked typeless philosophy. Components exchange explicit meanings and contracts rather than relying on shared implementation assumptions. A component may remain implementation language agnostic while its inputs, outputs, authority, lifecycle, and evidence requirements remain explicit. The system therefore separates what a component is allowed to receive, what it is allowed to produce, and what another component may conclude from that result.

The architecture also follows Unix atomic principles. Each component should perform one coherent responsibility, communicate through narrow interfaces, preserve durable state at explicit boundaries, fail closed when required evidence is absent, and make the smallest change necessary to advance the system. A repository is not treated as an owner merely because it contains similar code. Ownership follows the validated contract and the evidence attached to it.

The OmniKali system begins with the knowledge graph. The knowledge graph records ownership, dependencies, evidence status, known failures, goals, and boundaries. It informs Grasshopper about which component owns a responsibility and which claims remain unproven. Grasshopper then uses those facts to coordinate reproducibility and execution work. The knowledge graph therefore supplies architectural context to the control plane, but it does not execute desktop tasks itself.

Grasshopper acts as the reference control plane and reconstruction boundary. It defines domain contracts, durable state, resource ownership, exclusive locks, asynchronous task execution, recovery and reconciliation, deterministic export and import, executor boundaries, and agent interfaces. Grasshopper consumes architectural knowledge and production evidence from the coordination layer. It expresses those observations as reproducible contracts and tests. It sends task contracts toward execution systems rather than directly pretending to be the desktop.

The BIST system belongs to the Grasshopper control boundary. BIST converts acceptance expectations into explicit machine readable evidence. Grasshopper invokes BIST to determine whether a behavior has been proven, failed, not proven, or does not apply. BIST therefore prevents a successful local operation from being mistaken for a production capability. BIST also provides a gate between implementation changes and claims about system behavior.

The clean host reproducibility system belongs beside BIST and the Grasshopper control plane. It consumes the same contracts and attempts to establish whether an authorized agent can reproduce the system without undocumented operator intervention. It reports evidence back to the control and knowledge layers. It must not use production secrets merely to make a reconstruction test pass.

Helix supplies the protected production control plane and cloud desktop gateway. Grasshopper sends control contracts toward Helix when the task crosses from abstract orchestration into the validated production desktop boundary. Helix authenticates users, manages workspace and desktop lifecycle, supervises hypervisor resources, and exposes the browser compatible remote display path. Helix therefore converts control plane intent into authorized desktop lifecycle operations.

Helix persists control plane state through PostgreSQL. PostgreSQL stores durable information needed by the Helix service rather than serving as an informal message channel between unrelated components. Helix reads and writes that state according to its service contracts. Database failure is treated as a distinct failure boundary and must be tested as such.

Helix controls the hypervisor boundary through libvirt and QEMU. The control plane requests lifecycle operations through this boundary instead of manipulating guest processes as if they were ordinary application processes. Libvirt and QEMU create, maintain, and terminate the virtual machine boundary. The guest then supplies the operating system environment in which the remote desktop runs.

The helix omnikali guest receives the virtual hardware and lifecycle decisions produced by the hypervisor boundary. It provides the persistent Kali desktop environment. Its remote display path is consumed by the gateway rather than by the public discovery repository. The guest is therefore a runtime resource, not the public routing layer.

The production public path begins at the OmniKali public discovery layer. The omnikali repository publishes a stable entry point and an endpoint record. It probes the external endpoint before presenting a usable connection target. It therefore consumes health evidence and produces a safe discovery result. It does not manage QEMU, authenticate the guest, or implement the remote display protocol.

The older omnikali link repository provides a legacy public pointer and phone oriented shell. It points users toward a published OmniKali origin and can fail fast when that origin is unavailable. It does not own the workstation, authentication policy, QEMU lifecycle, or remote display implementation. The newer omnikali public door carries the active fail closed discovery responsibility.

The GitHub Pages repository onnxscibroccoli github io provides a publication and deployment surface for static public artifacts. It can publish an externally consumable representation of a component without becoming the component that owns the underlying runtime. Where the public door needs a stable published artifact, the Pages surface publishes it. It does not replace Helix or the workstation.

The external production path then reaches CloudFront. CloudFront provides the public edge for the validated production desktop path. It forwards requests to the protected gateway rather than becoming the desktop itself. The architecture records CloudFront as an edge boundary whose correctness depends on the downstream gateway being healthy.

Nginx receives the CloudFront traffic on the production host. Nginx routes traffic into the Helix service on its designated service boundary. Nginx therefore acts as an ingress and routing boundary. It should not be confused with the Kubernetes ingress prototype or with the public discovery layer.

The authenticated product path proceeds from CloudFront through Nginx and Helix into libvirt and QEMU, then into the helix omnikali guest, and finally back through the browser compatible remote display channel to the user. Each boundary owns one transformation. Authentication creates authorization. Helix creates or supervises a desktop session. The hypervisor provides the guest. The guest provides the desktop. The remote display layer provides pixels and input transport.

The separate noVNC host console is intentionally different. The CloudFront noVNC path reaches a host websockify service and then reaches the host VNC server. That path exposes the hypervisor console rather than the authenticated guest product path. It therefore must not be merged conceptually with the guest RFB path.

The kali node repository represents the persistent Kali workstation lineage. It supplies workstation level integration around the Kali desktop and connects with the production control plane. Helix provides the lifecycle and cloud control boundary while kali node provides workstation behavior and integration. The relationship is therefore complementary rather than duplicative. A change that attempts to make both repositories independently own the same desktop lifecycle creates an ownership collision.

The grasshopper kubernetes repository represents an alternative execution substrate. It develops isolated desktop instances using Kubernetes oriented components such as Guacamole and VNC. It consumes control plane ideas from Grasshopper and can provide a scalable desktop substrate. It remains a prototype and does not replace the validated Helix production origin. Its ingress must not claim production ports merely because the prototype works locally.

Apache Guacamole belongs to that Kubernetes prototype boundary. Guacamole translates browser oriented remote desktop interaction into a web accessible session. The Kubernetes repository can therefore use Guacamole to provide a browser desktop surface. The existing architecture does not treat Guacamole as equivalent to the Helix production RFB path until an acceptance test establishes that equivalence.

The kiln repository represents a browser contained alternative execution model. It explores a different way to provide computation inside the browser boundary. It can inform substrate research and alternative execution design, but it does not own the Kali production desktop path. Its relationship to Grasshopper is therefore experimental rather than a production dependency.

The GPT OmniKali full stack repository preserves recovery and implementation provenance. It contains a recovered workstation, historical orchestration code, public pointer history, tests, and deployment archaeology. Grasshopper uses this material as evidence when reconstructing lineage. The recovery repository must not be treated as current production merely because it contains working fixtures or historical implementation code. Its purpose is to preserve knowledge and distinguish recovered behavior from newly reproduced behavior.

Broccoli core supplies the Android execution and automation lineage. It contains the historical agent runtime, local execution kernel, provider abstractions, Android and Termux automation, state, tooling, and transport experiments. Grasshopper can consume the durable ideas and narrow contracts that are still validated. Grasshopper must not inherit the entire historical script collection merely because Broccoli contains it.

The Broccoli kernel follows a sequence in which text becomes an interpreted request, the request is classified, a schema is resolved, an action executes, and the result is confirmed. The important architectural relationship is not the historical implementation syntax. It is the separation between intent, execution, and confirmation. Grasshopper can use that philosophy when defining task contracts while keeping the production control plane independent of historical Broccoli implementation details.

The Android execution path begins at the Grasshopper MCP contract. The contract crosses into the Android and Termux execution boundary. The Android boundary invokes the known Rish wrapper. Rish then reaches the Android shell through the proven Shizuku environment. The Android shell interacts with the installed application or Android system. Evidence travels back through the same narrow execution boundary so the caller can distinguish actual output from a silent failure.

The Rish boundary is especially important because it prevents a caller environment failure from being misdiagnosed as a transport failure. The known good Rish invocation operates with the required sanitized environment and with environment preservation disabled. RDC and Termux do not have identical caller environments. Therefore the Android execution layer restores only required runtime variables instead of copying the entire Termux environment.

Remote Desktop Commander belongs on the caller side of this Android path. It initiates commands and receives execution results. It must consume the proven Broccoli and Rish transport rather than creating a second transport implementation. If RDC produces a zero exit status with empty output, the system treats that as insufficient evidence rather than success.

The Android native OmniKali MCP provides authenticated phone local control tools. It receives structured requests from the supervisory layer and performs bounded Android actions. The MCP supervisor monitors the MCP process and can recreate it after termination. That recovery behavior is proven as bounded supervisor recovery, not as a guarantee that Android will preserve every process across reboot, force stop, or battery management.

The APK first inspection layer consumes Android package and application evidence before attempting semantic UI automation. It identifies the installed application and then supplies the UI automation layer with grounded targets. This prevents an automation agent from acting on a guessed application state.

The semantic UI automation layer observes the installed application, selects a grounded target, performs an action, and verifies the resulting state. It therefore depends on actual runtime UI evidence. It must not substitute screenshots, stale selectors, or successful process exit codes for observed application state.

The Shizuku silent mic repository, the Android virtual mic Shizuku repository, and the Shizuku virtual mic repository are reserved Android experiments. Their current state is empty or reserved. They remain in the corpus so that the architecture does not confuse repository existence with implementation evidence. They do not currently provide a production dependency.

The Morphe ecosystem forms a separate Android modification dependency family. Morphe Manager receives patch source metadata and manages patch packages. Morphe Desktop provides desktop tooling around that ecosystem. The patch repositories provide source registries and source specific patch lineages. The patch template provides a development template. Grasshopper and Broccoli can coordinate Morphe related work when an Android automation task requires it, but Morphe source availability does not prove installation or runtime success.

Morphe patch verification is therefore a multi step boundary. A patch source must provide metadata and compatible target information. Where signatures or releases are relevant, those must be verified. The patch must then be processed by the Morphe tooling. Finally the Android runtime must provide confirmation that the intended modification is installed and active. Repository presence alone is not installation evidence.

The noVNC repository is an upstream dependency fork used by the remote desktop family. It provides browser based VNC display functionality that can be integrated into a gateway or console path. It does not own the OmniKali control plane. Its role is therefore dependency implementation rather than system orchestration.

The oauth2 proxy repository is an upstream authentication dependency fork. It can provide authentication and authorization boundary behavior where a compatible deployment uses it. It does not own the OmniKali user model or the Helix control plane. Its role remains an authentication dependency rather than an independent product boundary.

LATTICE is an adjacent rules and research system. It converts a written thesis into explicit rules, evidence requirements, tests, and execution records. It operates with a fail closed philosophy similar to the broader architecture, but it is not part of the OmniKali desktop runtime. Its relationship to the knowledge graph is informational and potentially complementary. The graph can record its status and evidence without making LATTICE a hidden production dependency.

LATTICE audit is the public audit boundary for LATTICE. It exposes methodology and audit material without becoming the private LATTICE engine. It therefore consumes selected public evidence from LATTICE and exposes it for review. It remains an adjacent product boundary.

The published newsroom desk application is an independent application in the repository corpus. It can share general publication, web application, authentication, or deployment techniques with other projects, but the current system graph does not establish it as an OmniKali runtime dependency. Its relationship is therefore repository level coexistence rather than operational coupling.

The half a mile application is another independent published application. It contains editorial content, citations, authentication, database behavior, and dynamic and static publication. Those mechanisms may provide reusable engineering patterns, but the current architecture does not establish a direct runtime dependency on OmniKali.

DECtalk Live is a browser contained speech synthesis application. It performs synthesis locally in the browser through WebAssembly and uses browser isolation support for threaded execution. It is independent of the OmniKali desktop runtime. Its presence in the corpus demonstrates another published browser application rather than a production desktop dependency.

The two GitHub write test repositories are completed capability probes. They exist to establish that repository write or integration capabilities can be exercised. They are archival evidence rather than runtime dependencies. The knowledge graph keeps them visible so historical capability claims remain distinguishable from current production components.

The knowledge graph master repository coordinates all of these boundaries. It consumes evidence from repositories, tests, acceptance artifacts, and implementation history. It records the resulting ownership and status. It then informs future agents before they modify a repository. This makes the graph a coordination system rather than an execution service.

The entire architecture is governed by evidence flow. A component may describe an intended capability, but another component must not treat that description as proof. Live acceptance outranks implementation claims. Explicit production contracts outrank summaries. Verified source implementation outranks historical screenshots. The graph records this authority order so that future work can remain conservative.

The architecture is also governed by ownership flow. When two repositories appear to own the same responsibility, the system stops and resolves ownership before adding another implementation. This is why Helix and grasshopper kubernetes remain separate desktop paths, why Broccoli transport is reused instead of duplicated, why the public door does not become a workstation, and why recovery code is not silently promoted to production.

The architecture is governed by failure containment. A failure at one boundary should not cause another proven lower layer to be rewritten without evidence. A caller failure should remain a caller failure until transport evidence shows otherwise. A stale endpoint should not be published. A local fixture pass should not become a live acceptance claim. A prototype ingress must not displace a protected production ingress.

The architecture is governed by durable state. Task state belongs in a durable control plane when execution must survive process failure. Workspace state belongs with the workspace. Public endpoint state belongs in the published endpoint record. Evidence belongs in dated evidence documents. Historical provenance remains preserved instead of being rewritten into a cleaner but less truthful history.

The architecture is governed by narrow interfaces. Intent becomes a task contract. The task contract becomes an execution request. The execution request becomes a runtime operation. The runtime operation produces evidence. Evidence becomes an acceptance result. Acceptance results update the knowledge graph. Each boundary exposes only the information needed by the next boundary.

The architecture is therefore typeless at the implementation language level but typechecked at the contract level. A caller does not need to know which programming language implements the callee. The caller does need to know what input is accepted, what output is returned, what authority is required, what evidence proves success, and what failure states are possible.

The final relationship is between development and truth. Development changes implementation. Verification tests implementation. Acceptance tests behavior. Evidence records behavior. The knowledge graph records ownership and dependency consequences. No layer is permitted to promote an unproven claim merely because it makes the architecture look complete.

This narrative is intentionally plain text so that it can be read by text to speech systems, indexed by agents, compared across versions, and converted into other representations without first interpreting a diagram. The machine readable graph remains the structured dependency representation. This narrative remains the human and voice oriented explanation of those same relationships.

The current architecture therefore does not need another parallel system. It needs dependency ordered execution, small atomic changes, narrow tests, explicit acceptance, and continuous evidence updates. The protected Helix production path remains the reference runtime. Grasshopper remains the reconstruction and control plane. Kali node remains the workstation lineage. Broccoli remains the Android execution and automation lineage. The public OmniKali repositories remain discovery and publication boundaries. Kubernetes and kiln remain alternative execution research until their acceptance gates prove otherwise. The knowledge graph remains the coordination layer that keeps those boundaries explicit.
